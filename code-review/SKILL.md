# Code Review Skill

## Step 0: 锚定审查对象与证据
**输入**：用户的审查请求（PR/分支/commit/文件/片段/全仓）+ 可用的基线
**输出**：审查模式、固定基线、变更范围证据

先区分审查模式，避免把历史遗留问题、需求猜测和当前变更混在一起：

| 审查对象 | 必做动作 | 审查边界 |
|-----------|----------|----------|
| PR、分支、commit 或工作区改动 | 要求用户给出固定基线；验证 `git rev-parse <base>`，记录 `git diff <base>...HEAD` 和 `git log <base>..HEAD --oneline`，确认 diff 非空 | 只对该 diff 负责；未改动的遗留问题单列为范围外观察 |
| 单个文件、函数或代码片段 | 明确缺失的调用方、配置、硬件描述或测试上下文 | 仅基于已提供材料审查，不推断仓库级需求符合性 |
| 全仓或模块健康检查 | 明确扫描路径、时间预算和优先目标 | 报告中标明这不是增量 PR 审查 |

🛑 **STOP — 基线或输入不可用？**
| 条件 | 动作 |
|------|------|
| 增量审查未提供基线 | 请求 commit、分支、tag 或 `main`；不要自行猜测比较对象 |
| 基线无效或 diff 为空 | 报告该事实并停止增量审查；不要把空 diff 扩展为全仓审查 |
| 无 Git 仓库或用户仅提供片段 | 使用片段模式，并在结论中标注无法验证变更范围 |

## 审查流程

### Step 1: 理解上下文
**输入**：用户提供的代码 / PR / commit diff（基于 Step 0 固定的基线）+ 上下文描述
**输出**：审查范围摘要（语言、框架、变更范围、审查目标）+ 已定位的可验证证据来源（需求/规范/硬件资料）

读取代码后，列出：
1. **代码目的**：这段代码实现什么功能
2. **变更范围**：修改了哪些部分、为什么
3. **业务背景**：相关需求或用户故事
4. **技术栈**：语言、框架、工具
5. **语言/领域检测**：根据文件扩展名和代码内容判断语言与领域
6. **可验证证据**：需求来源、项目规范、硬件/协议资料、已执行的构建或测试

🛑 **STOP — 上下文不足？**
| 条件 | 动作 |
|------|------|
| 代码片段不完整（缺少关键函数/文件） | 向用户请求补充，标注缺失范围后再继续 |
| 无法判断语言/框架 | 向用户确认技术栈 |
| 无明确的审查目标 | 默认进行全维度审查（功能→安全→性能→质量→测试→文档→架构） |

### Step 2: 建立双轨证据
**输入**：Step 1 的上下文摘要 + 已定位的需求/规范来源
**输出**：Spec 与 Standards 两条独立证据链

在检查实现之前，分别建立不可混淆的 **Spec** 与 **Standards** 证据链：

1. **Spec（需求符合性）**：按 commit/PR 中的 issue 引用、用户提供路径、`docs/`/`specs/`/`.scratch/` 中的需求文档顺序定位来源。BIOS/BMC 变更还要定位对应的协议、平台规格、寄存器定义或硬件勘误。
2. **Standards（规范符合性）**：读取仓库内的 `AGENTS.md`、`CONTRIBUTING.md`、编码规范、模块 README、构建规则和静态检查配置；再使用 `resources/REVIEW-CHECKLIST.md` 补足通用检查。
3. **优先级**：仓库规范及已确认的硬件/协议一手资料，高于通用 checklist 和设计异味启发式。未找到一手资料时，不把硬件行为猜测写成事实。

🛑 **STOP — 证据不足？**
| 条件 | 动作 |
|------|------|
| 未找到需求或规格 | 请求来源；若仍不可得，Spec 轨明确写为“无规格，无法判定需求符合性”，继续做实现质量审查 |
| 硬件行为只能依赖猜测 | 标注“需平台/硬件专家确认”，说明需要的资料，不臆测寄存器、副作用或时序 |
| 规范相互矛盾或明显过时 | 引用冲突来源，优先采用当前模块或项目根目录的规范，并把结论标为待确认 |

### Step 3: 语言/领域专项激活
**输入**：Step 1 检测到的语言/领域
**输出**：激活的专项检查清单，或回退通用审查清单

根据 Step 1 检测到的语言和领域，激活对应的专项检查清单：

| 语言/领域 | 专项检查项 |
|-----------|-----------|
| **C/C++** | 指针安全（野指针、悬垂、use-after-free）、内存管理（malloc/free 配对、buffer overflow、double-free）、undefined behavior、`volatile` 正确使用、栈溢出风险；C++ 额外：RAII、智能指针、移动语义、rule-of-five、内存对齐、ABI 兼容性；静态分析：Cppcheck、Clang-Tidy |
| **嵌入式通用** | 中断安全（ISR 中禁止阻塞调用）、`volatile` 与 MMIO 正确使用、硬件寄存器访问（原子性、位操作）、内存约束（栈大小、堆碎片）、bare-metal 最佳实践（无 OS 环境下的并发）、看门狗喂狗、功耗关注点 |
| **BIOS/UEFI** | ACPI 表长/校验和与 SMBIOS Type 规范、UEFI Protocol 契约、硬件初始化顺序、SEC/PEI/DXE/TSL 阶段边界和 HOB 生命周期、S3 恢复、Secure Boot/认证变量、SMM 输入验证与 SMRAM 边界 |
| **BMC** | IPMI 请求长度/权限/完成码、传感器转换/阈值/滞回、Watchdog 失效路径、Redfish Schema/权限/错误映射、D-Bus 异步对象生命周期、systemd 服务状态、I2C/SMBus 超时重试与总线并发、主机电源/复位的安全状态 |
| **Python** | 类型安全、GIL 影响、依赖安全、duck typing 边界 |
| **Java/Go/Rust** | 各语言惯用模式和常见陷阱 |

### BIOS/BMC 原始数据与不可信边界

激活 BIOS/UEFI、BMC 或嵌入式专项时，额外检查以下内容，并把结论绑定到规格或代码证据：

1. **原始硬件数据**：对 I2C/SMBus/SPI/PECI/MMIO 的读数，核对字节序、符号位、位域、缩放单位、量程、对齐和转换溢出。仅知道目标单位（例如摄氏度）不足以证明编码和缩放正确；缺少数据表或平台定义时，必须在报告中写为“需确认解码契约”，不要将 `raw / N`、字节序或精度假设断言为缺陷。
2. **通信与长度**：对不可信缓冲区，分别核对并报告每个指针参数的 `NULL`、总长度、最小固定头部、载荷范围、目标容量和地址空间边界。长度关系必须先排除下溢或溢出，例如先确认 `total_len >= header_len`，再验证 `payload_len <= total_len - header_len`；修复示例不得以 `start + length <= end` 代替该减法式范围检查。目标容量检查不能替代载荷仍位于输入缓冲区内的检查；不清楚载荷是指针还是柔性数组时，标注需要结构体定义。检查 `CopyMem`、数组索引、地址加偏移和整数转换的边界。
3. **检查后使用**：当调用方、DMA 或并发执行体能在校验后修改输入时，检查 TOCTOU 风险；报告中明确说明是否已在可信内存中复制经验证的数据，或该事实待确认。通信缓冲区地址、长度或载荷校验缺失的标签必须写为“输入范围校验缺失”。禁止仅凭这类缺失使用 “SMM callout”、“Callout/Oracle” 或类似标签；只有代码实际执行外部函数指针、非 SMM 服务或不可信回调时才可使用该术语。
4. **时序结论**：只有引用的需求、协议或平台规格给出阈值时，才报告时序违规；阈值或硬件限制未知时，报告验证缺口和所需资料。

如果未匹配到任何专项，使用通用审查清单（参考 `resources/REVIEW-CHECKLIST.md`）。

🔴 **STOP — 领域不熟悉？**
| 条件 | 动作 |
|------|------|
| 代码涉及不熟悉的硬件架构/芯片手册 | 坦诚说明局限，审查逻辑和代码质量，对硬件特定行为标注"需硬件专家确认" |
| 代码依赖特定的 SDK/BSP 且无法获取文档 | 标注受审查影响范围，跳过 SDK 内部逻辑 |

### Step 4: 结构化审查
**输入**：Step 2 的 Spec/Standards 双轨证据链 + Step 1 的审查范围摘要 + Step 3 的激活专项清单
**输出**：包含 🔴/🟡/🟢 分级的发现列表

按优先级逐项检查，参考 `resources/REVIEW-CHECKLIST.md` 逐项过检：

| 优先级 | 维度 | 说明 |
|--------|------|------|
| 🔴 必须修复 | 功能正确性、安全性、严重 Bug | 代码未实现预期功能 / 存在注入漏洞 / 逻辑导致崩溃 |
| 🟡 强烈建议 | 性能、测试覆盖、错误处理、架构 | 有可量化的负面影响：N+1 查询（QPS 下降 >10%）、缺少单元测试（覆盖率 <80%）、异常被吞掉（静默失败）、循环依赖（编译/加载失败） |
| 🟢 建议 | 代码质量、文档、最佳实践 | 无量化影响但影响可维护性：命名不清 / 缺少注释 / 风格不一致 |

要求：
- 先分别完成 **Spec**（需求、协议、平台规格）与 **Standards**（项目规范、通用质量）的审查，再汇总发现；两条证据链不得相互替代
- 子代理可用时并行执行两个审查轨；不可用时以两个独立 pass 执行，并在报告中标明执行方式
- 每个发现标注优先级、类别（Spec/Standards/安全/平台）、所在行号或函数、证据来源、影响和修复方向
- 🔴 项必须附完整修复示例或明确替代方案，并说明触发条件或复现路径
- 只记录有具体证据的优点；没有则省略，不得为满足格式虚构正向结论
- 能运行验证时，优先执行与改动相符的最窄构建、静态分析、单元测试、QEMU 或硬件验证；无法执行时明确标注为静态审查结论

🛑 **STOP — 审查范围失控？**
| 条件 | 动作 |
|------|------|
| PR/diff 超过 400 行变更 | 向用户建议拆分审查范围（按模块/功能分批），或仅审查核心逻辑路径 |
| 单次审查反馈超过 30 条 | 分两批输出：先输出所有 🔴 + 🟡，再输出 🟢 |
| 代码无法编译运行 | 明确标注"审查基于静态分析，运行时行为未验证"，优先修复编译错误 |

对 BIOS/BMC 改动，将专项检查与 Spec/Standards 交叉验证：例如，IPMI/Redfish 的需求结论必须能追溯到协议或平台规格，`volatile`、寄存器访问和初始化顺序的规范结论必须服从已确认的项目规则与硬件资料。

### Step 5: 选择最窄验证路径
**输入**：Step 4 的 🔴/🟡 发现列表
**输出**：每项发现的验证计划（证据来源、最窄动作、可证实行为、状态、限制）

对每个 🔴/🟡 发现制定验证计划，先检查变更目录及父目录中的现有构建文件、测试、CI 配置和 `compile_commands.json`；项目已有命令优先于通用工具名。每项验证都要写明 **证据来源、最窄动作、能证实的行为、状态和限制**。

| 发现类型 | 选择顺序与边界 |
|-----------|----------------|
| 可由现有测试复现的行为 | 先执行覆盖变更的单个测试文件、测试用例或模块 target；未发现定向测试时，记录该缺口，不以全量构建替代行为验证 |
| 编译、类型或内存边界 | 先从构建元数据或 CI 配置发现包含变更文件的 target；未发现 target 时，验证状态只能记录“需发现 target”，可列出读取构建元数据的发现动作（例如 Meson 的 target 列表），不得列出 `ninja`、`make`、`meson compile` 或构造的对象文件/target 命令。发现 target 后才可列对应构建命令。`compile_commands.json` 只提供编译上下文，不能证明某个静态分析器可用；只有项目配置或当前环境确认分析器后，才提出对应的静态分析命令。静态检查通过不等于协议、状态机或硬件行为正确 |
| BMC D-Bus、Redfish 或主机状态流转 | 可用镜像和模型已存在时，QEMU 可验证服务启动、对象状态和接口流转；没有镜像/模型时标为未执行。QEMU 不能证明物理 I2C/SMBus/GPIO 时序、仲裁或异常恢复 |
| BIOS/UEFI/SMM 边界 | 构建、单元或 host-based 测试只能验证可达路径和输入处理；不得据此宣称 SMRAM 隔离或芯片级 SMI 锁定安全。此类结论仍需平台安全审计与物理机专向验证 |

不要虚构命令结果、测试覆盖或硬件能力。无法执行时，写明缺失的命令、镜像、模型、工具链、测试或硬件条件，并把它保留在 `验证状态` 中。

### Step 6: 输出审查报告
**输入**：Step 2 的 Spec/Standards 证据链 + Step 4 的发现列表（含领域专项发现）+ Step 5 的验证计划
**输出**：结构化审查报告（Markdown）

输出格式：

```raw
## 代码审查报告 → [文件名/模块名]

### 发现摘要
[按严重度列出数量；没有发现时明确说明“未发现可操作问题”，并保留测试或证据缺口]

### 🔴 必须修复（N 项）
1. **[安全][文件:L42]** buffer overflow：`memcpy` 目标缓冲区仅 64 字节，源数据可达 256 字节
   - 证据：`sizeof(buf)` 与 `src_len` 未比较
   - 影响：可覆盖栈数据并导致固件异常或安全边界失效
   - 修复：`memcpy(buf, src, min(src_len, sizeof(buf)))`

### 🟡 强烈建议（N 项）
1. **[Spec][文件:L78-82]** 传感器轮询间隔与平台规格不一致
   - 证据：平台规格 [来源] 要求的间隔为 [值]
   - 修复：从平台配置读取并为超时路径增加验证

### 🟢 建议（N 项）
1. **[Standards][文件:L15]** 函数名 `read_data` 未表达传感器和单位
   - 修复：改为 `read_sensor_value`

### Spec 结论
- 已核对的需求/协议来源：[路径或链接]
- 缺失、错误或超出需求范围的行为：[发现编号或“无”]
- 无法判定项及原因：[来源缺失、硬件资料待确认等]

### Standards 与平台专项结论
- 已核对的项目规则和专项资料：[路径或链接]
- C/嵌入式/BIOS/BMC 专项发现：[发现编号或“无”]

### 验证状态
- [已执行/未执行] [最窄动作或命令]：证据来源、可证实行为、结果或缺失条件
- 验证边界：[不能由当前构建、静态分析、QEMU 或硬件动作证明的事项]

### 下一步
1. 先修复所有 🔴 项并执行对应验证
2. 再处理 🟡 项
3. 提交后以相同基线重新审查
```

参考 `resources/FEEDBACK-GUIDELINES.md` 撰写反馈措辞。

### 端到端示例（核心步骤节选，跳过 Step 2 证据建立与 Step 5 验证规划）

**输入**（用户请求）：
> 帮我 review 这段 C 代码：`sensor_read.c`（内容略，含 buffer overflow + 缺少 volatile）

**Step 1 输出**：语言=C，领域=嵌入式/BMC，变更=传感器读取模块，目标=全面审查

**Step 3 激活**：C 专项（内存管理、volatile）+ 嵌入式通用专项（中断安全、MMIO）+ BMC 专项（传感器阈值）

**Step 4 发现**：
- 🔴 L18: `memcpy(buf, data, len)` — len 未校验，buffer 仅 64 字节
- 🔴 L34: `*reg = value` — 缺少 `volatile`，编译器可能优化掉硬件写操作
- 🟡 L52: 轮询间隔硬编码为 100ms — 不同传感器需不同采样率
- 🟢 L7: 函数名 `read_data` 建议改为 `read_sensor_value`

**Step 6 输出**：按报告模板输出，🔴 项附修复代码，原文引用 MISRA-C:2012 Rule 11.4（指针转换）。

## 禁止事项（Blacklist）

| # | 禁止行为 | 原因 |
|---|---------|------|
| B1 | 只写 "LGTM" / "看起来没问题" 就结束 | 未进行实质审查，可能遗漏严重问题 |
| B2 | 只批评不给修复方向 | 不建设性，浪费作者时间；🔴 项必须附修复代码 |
| B3 | 使用讽刺、居高临下的措辞 | 违反专业代码审查准则；参考 `FEEDBACK-GUIDELINES.md` |
| B4 | 跳过安全检查 | 即使代码看似非安全敏感，也必须检查输入验证和数据处理 |
| B5 | 照抄代码做"格式化审查" | 不要仅做格式调整就当作审查结果，必须关注逻辑和架构 |
| B6 | 对不熟悉的领域假装权威 | 坦诚标注审查边界（"需硬件专家确认"），而非臆测硬件行为 |
| B7 | 忽略用户的特定审查请求 | 如果用户只要求安全审查，不要强加性能/测试建议；尊重审查范围 |
| B8 | 以通用 checklist 或设计异味推翻项目规范、EDK2/MISRA 规则或硬件资料 | 通用规则只是启发式；以仓库规范与一手资料为准 |
| B9 | 把未经证实的寄存器副作用、时序或平台行为写成事实 | 缺少规格时必须标注待硬件专家确认，并说明需要的证据 |
