# 固件专项检查：原始数据与不可信边界

激活 BIOS/UEFI、BMC 或嵌入式专项时（见 `SKILL.md` Step 3），额外检查以下内容，并把每条结论绑定到规格或代码证据。先按 `SKILL.md` Step 2 的优先级与双轨模式确认证据来源。

## 1. 原始硬件数据

对 I2C/SMBus/SPI/PECI/MMIO 的读数，核对字节序、符号位、位域、缩放单位、量程、对齐和转换溢出。仅知道目标单位（例如摄氏度）不足以证明编码和缩放正确；缺少数据表或平台定义时，必须在报告中写为“需确认解码契约”（**待确认**），不要将 `raw / N`、字节序或精度假设断言为缺陷。

## 2. 通信与长度

对不可信缓冲区，分别核对并报告每个指针参数的 `NULL`、总长度、最小固定头部、载荷范围、目标容量和地址空间边界。长度关系必须先排除下溢或溢出：先确认 `total_len >= header_len`，再验证 `payload_len <= total_len - header_len`；修复示例不得以 `start + length <= end` 代替该减法式范围检查。目标容量检查不能替代载荷仍位于输入缓冲区内的检查；不清楚载荷是指针还是柔性数组时，标注需要结构体定义。检查 `CopyMem`、数组索引、地址加偏移和整数转换的边界。

## 3. 检查后使用（TOCTOU）

当调用方、DMA 或并发执行体能在校验后修改输入时，检查 TOCTOU 风险；报告中明确是否已在可信内存中复制经验证的数据，或该事实 **待确认**。通信缓冲区地址、长度或载荷校验缺失的标签必须写为“输入范围校验缺失”。禁止仅凭这类缺失使用 “SMM callout”、“Callout/Oracle” 或类似标签；只有代码实际执行外部函数指针、非 SMM 服务或不可信回调时才可使用该术语。

## 4. 时序结论

只有引用的需求、协议或平台规格给出阈值时，才报告时序违规；阈值或硬件限制未知时，报告验证缺口和所需资料。

## BIOS/BMC 与双轨交叉验证

将专项检查与 Spec/Standards 交叉验证：IPMI/Redfish 的需求结论必须能追溯到协议或平台规格；`volatile`、寄存器访问和初始化顺序的规范结论必须服从已确认的项目规则与硬件资料。
