# 代码审查反馈指南

撰写审查报告措辞时参考（报告结构见 `SKILL.md` Step 6，发现字段见 Step 4）。先按 `SKILL.md` Step 2 的双轨与优先级确认证据。

## 反馈原则

- 聚焦代码与证据，不针对作者：说“这个函数可以更简洁”，不说“你写得太复杂”。
- 每条发现附：行号、证据来源、影响、修复方向（与 `SKILL.md` Step 4 字段一致）。
- 不确定的发现用提问式，不臆断意图；无法证实的标注 **待确认**。

## 反馈模式

- **提问式**：意图不明或推断不确定时——“这里为什么选择 X 而非 Y？”“这个逻辑能否处理边界 Z？”
- **建议式**：给具体改进及理由——“建议将 200 行函数拆为 `extractX()` / `validateY()`，理由：可测试性。”
- **解释式**：说明原因与影响，安全/性能类常需此模式——见下方场景示例。
- **赞赏式**：仅对有具体证据的优秀实践给予肯定（Step 4 已要求只记录有证据的优点）。

## 常见反馈场景（措辞示例）

**🔴 安全**：`🔴 必须修复：硬编码密码。影响：敏感信息泄露。建议：移至环境变量或密钥管理服务。触发：部署到任意环境即泄露。`

**🟡 性能**：`🟡 强烈建议：循环内查询导致 N+1。影响：数据量增大时 QPS 下降 >10%。修改前：循环内单条查询；修改后：JOIN 或预加载。`

**🟢 代码质量**：`🟢 建议：函数名 \`doStuff\` 未表达意图。建议：按实际功能改为 \`validateEmailFormat\`。`

**🟡 测试缺失**：`🟡 强烈建议：新功能缺单元测试。建议补：正常成功 / 边界（空、最大、最小）/ 异常处理三类用例。`

**🟢 文档不足**：`🟢 建议：公共 API 缺文档注释。建议补 @param / @returns / @throws 与使用示例。`

**🟡 位置待重锚定**：该发现引用的代码位置无法精确锚定到当前 diff（可能因跨文件推断或行漂移）。已在发现上标注“位置待重锚定”；请人工结合上下文复核具体落点。

**验证状态段**：证伪自检：自否决降级/移除 N 条 🔴🟡 发现（理由：diff 提供直接反证 — <简述反证>）。此操作未静默，保留可审计记录。
